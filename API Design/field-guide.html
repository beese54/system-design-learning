API Design Field Guide

An API is a promise about behaviour across a boundary. Everything that follows — the URL shapes, the status codes, the schema files, the arguments about protocols — is bookkeeping on that one idea. This is the reference companion to the hands-on course; the numbers in it were measured, not quoted.

01 What an API actually is

One side agrees to accept certain messages and answer in a certain shape. The other agrees to ask only in that vocabulary. Everything past the promise — language, database, deploy schedule — stays private and swappable. That ignorance is the product.

Client

Web app, mobile app, another service.

knows the contract, nothing else
request

The contract

URL · method · payload shape · status codes · error format · limits · versioning

the only thing both sides depend on
response

Implementation

Business logic, database, caches, other services.

free to change while the promise holds

Anything a consumer can observe and depend on is part of your API, whether you meant it or not — including the list ordering you never promised and somebody is relying on right now.

02 Where APIs sit in a system

Architecture is the question where do we cut? An API is a cut you committed to. Draw any system: the arrows crossing boxes are its APIs, and the boxes are independent only to the degree those arrows are well designed.

The protocol changes at the edge, and that is not fashion: each side is optimising for a different consumer. Cross-cutting concerns — auth, quotas, TLS, logging — belong in one place, or you will ship eight subtly different implementations and one incident.

The most common architecture mistake is applying internal rules to a public API, or public rules to an internal one.

03 The principles that survive protocol choice

These hold for REST, GraphQL and gRPC alike. The protocol changes how you honour them, never whether you should.

Design for the job, not the schema

If you cannot rename a database column without a client noticing, you published your schema, not an API.

Consistency beats cleverness

One casing, one date format, one money representation, one error shape. A developer should be able to guess the next endpoint.

Names are the interface

You will rewrite the implementation three times and the vocabulary never. Use the words the business already says out loud.

Keep the surface small

Every field is a lifetime commitment: documented, tested, secured, migrated. Adding one later is trivial; removing one is not.

Errors are a feature

Right status, one body shape, actionable detail, a retry signal, and no stack traces. Integrators handle errors more than anything else you ship.

Assume every request arrives twice

Safe methods change nothing; unsafe ones take an idempotency key and return the first result on a retry.

Paginate and cap from day one

Retrofitting pagination is a breaking change. Cursors over offsets; cap the page size server-side whatever the client asks for.

Evolve additively

Add fields freely. Removing, renaming, retyping or making something required is a new version and a deprecation plan.

Authorise per object

Authentication says who; authorisation says whether they may touch this record. The classic breach is a valid login plus an unchecked id.

Docs are part of the product

A machine-readable spec, a quickstart that works when pasted, an error catalogue, limits, and a changelog.

The same failure, twice

04 How the protocol shapes the design

Your protocol is not a delivery detail chosen after the design. It decides which ideas are cheap, which are expensive, and which are impossible.

What HTTP gives you free — if your design lets it

FeatureUnlocked byLost when…
Methodsverb in the method, noun in the URLeverything is POST /graphql
Status codesoutcome in the status lineyou return 200 with an error body
Caching, 304each thing has a stable URLone URL serves every possible response
Content negotiationresource separate from representationthe format is baked into the path
Proxies, CDNs, curlspeaking plain HTTPyou invent a framing on top

The version that created two design styles

ProtocolConcurrencyWhat it made cheapDesign pressure
HTTP/1.1one request at a time per connectionsimplicity, debuggabilityround trips are scarce → compound documents, ?expand=, eventually GraphQL
HTTP/2multiplexed streams, compressed headersmany small calls, long-lived streamsfine-grained resources become affordable; gRPC requires it
HTTP/3QUIC over UDP, no TCP head-of-line blockinglossy networks, faster handshakesmostly free performance, same design

Serialisation is a design decision too

JSON is self-describing, debuggable with your eyes, and verbose. Protobuf puts field numbers on the wire, not names: typically 30–70 % smaller, parsed as a memory copy rather than a string scan — and unreadable without the .proto. Legibility is a real feature; it is just not always the most valuable one.

05 Three styles, one dataset

Same music catalogue — artists → albums → tracks — exposed three ways. Every difference below is a design difference, not a data difference.

Resources

REST

Things with addresses, manipulated with a fixed set of verbs. The server decides the shape.

GET /v1/artists/a1/albums

200 OK
ETag: "242db43c060dca90"
Cache-Control: public, max-age=60

{ "data": [ … ],
  "page": { "next": "…cursor=YTI" } }
Buys you
HTTP caching, universal tooling, obvious debugging, strangers can integrate today
Costs you
round-trip waterfalls; over- and under-fetching; no native streaming
Use when
public and partner APIs, resource-shaped domains, read-heavy traffic
Query language

GraphQL

One endpoint, one type graph. The client declares the response shape, per query.

POST /graphql

{ artist(id: "a1") {
    name
    albums { title
             tracks { title seconds } } } }

→ exactly those fields, one round trip
Buys you
no over-fetching, one trip per screen, a schema that is also the docs and the types
Costs you
HTTP caching, status codes, predictable cost — you rebuild all three yourself
Use when
many client shapes over one graph; a BFF aggregating services
Procedures

gRPC

Typed function calls compiled from a .proto, binary over HTTP/2.

service CatalogService {
  rpc GetArtist  (GetArtistRequest)
      returns (Artist);
  rpc WatchPlays (WatchPlaysRequest)
      returns (stream PlayEvent);
}
Buys you
compiler-enforced contracts, small fast payloads, four streaming modes, deadlines everywhere
Costs you
no browser without a gateway, no HTTP caching, codegen in CI, harder debugging
Use when
service-to-service inside your perimeter, high volume, polyglot teams

06 The same screen, measured

Scenario: render one artist page — the artist, their albums, and every track on every album. Same data, same machine, three contracts.

Round trips per screen

Each one pays the full network latency. On a mobile network that is 80–150 ms per call before your server does any work at all.

Most real systems answer all three: gRPC between services, REST or GraphQL at the edge, events for anything that must not block. "Which one" is the wrong question; "which one here" is the right one. And one row of the decision table is not a joke — an API style your team can debug at 3 a.m. beats a better-suited one they cannot.

08 The design process

The order matters more than the ceremony. Each step is cheap where it sits and brutally expensive one step later.

01

Find the jobs, not the tables

What is each consumer trying to accomplish, in their words? Note their constraints — slow network, no proxy, cannot ship for six weeks.

produces → use cases with the actor named
02

Model the domain

Nouns, relationships, identity. Opaque IDs, never row numbers. Get the vocabulary right; it outlives every implementation.

produces → an entity sketch with cardinality
03

Choose the style deliberately

REST, GraphQL, gRPC, events. "It is what we know" is a valid reason. An unrecorded one is not.

produces → one defensible paragraph
04

Design the contract, before the handler

OpenAPI, SDL or .proto — including the error shape, pagination, limits and auth. Writing it forces the decisions into the open while they are still free.

produces → a spec file, reviewed on its own
05

Prototype against the contract

Mock it and have a real consumer build a real screen. Every question they ask is a naming failure or a docs gap.

produces → a client screen, and a list of edits
06

Review it like a publication

What happens on retry, on partial failure, on a client three versions old? Can a caller reach another tenant's object by changing an id?

produces → a signed-off contract + change policy
07

Ship the operational parts too

Docs that run, rate limits, per-consumer usage metrics, a changelog. You cannot deprecate what you cannot measure.

produces → docs, dashboards, limits, changelog

09 Living with it afterwards

Once someone integrates, your contract is a liability you maintain. The classification is the same everywhere; only the remedy differs.

ChangeRESTGraphQLgRPC
Add a fieldsafesafe — nobody selects it unaskedsafe — new tag number
Rename a fieldbreaking → new versionbreaking → add, @deprecated, measure, removefree on the wire, breaking for generated code
Make optional requiredbreakingbreakingbreaking in practice — proto3 cannot enforce it
Change a field's typebreakingbreakingbreaking and dangerous — add a new tag, reserve the old
Remove a fieldbreakingbreaking, but field-usage stats prove who is affected firstbreaking — reserved the tag forever

The deprecation playbook: announce with a date, measure usage per consumer, contact the top consumers directly, brown-out near the date so quiet clients notice while it is still recoverable, then remove with an error that names the replacement.
