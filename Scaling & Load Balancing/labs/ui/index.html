Capacity

Nothing else in this lab is trustworthy until this tab has run. It measures your machine, the work unit, the platform's timer and the load generator's own ceiling — and only then measures a server. A benchmark that has not calibrated its own instruments is a rumour.

Calibrates the work unit, measures the timer floor, finds the driver's ceiling.

Find the knee

One instance, one worker. Push concurrency up and watch throughput flatten while latency does not.

Coordinated omission

The same server, measured two ways. Most load tests do the first one and believe the answer.

The noise floor

Four identical runs. Whatever they disagree by is the smallest difference worth believing anywhere in this lab.

Little's Law

Throughput = concurrency ÷ latency. Past the knee throughput is fixed, so extra concurrency can only turn into latency. That is the whole of it.

Why the ceiling matters

A load generator has a capacity too. Any run above 70% of it is measuring the instrument, and the lab marks those rather than reporting them.

Why interleaved

Sweeps never run in ascending order. A laptop throttles under sustained load, and an ascending sweep turns that cooling curve into something that reads exactly like diminishing returns.

Vertical scaling

One instance, more workers inside it. cluster forks N processes sharing one listening socket — this is what "buy a bigger box" looks like from the inside. Watch where the return on each extra worker disappears, and note that the cores on this machine are not all the same speed.

The four ceilings

Cores, the event loop, memory, and the fact that one box can still die. Vertical scaling runs out of the first three and does nothing at all about the fourth.

Not all cores are equal

Modern laptop chips mix performance and efficiency cores. Node cannot tell them apart, so the lab does not claim to — it charts per-worker throughput and lets the spread speak.

What it does not fix

Every worker is a separate process with its own memory. Anything you kept in a module-level variable is now wrong in N different ways.

Horizontal scaling

More instances, one worker each, behind the balancer. Same total parallelism as the vertical sweep at every point, so the two curves are directly comparable.

The control experiment

The one measurement that decides what this chapter is allowed to claim. Same total request concurrency; the only change is how many processes serve it. If N instances and 1 instance land in the same place, then instance count was never the causal variable — concurrency was.

The balancer

Five policies, each a few lines of readable code. On a healthy fleet of identical instances they are indistinguishable — the choice only matters once the backends stop being interchangeable, which is why this tab injects a fault by default.

The zombie

An instance that fails instantly has the lowest latency and the fewest in-flight requests in the pool — so the cleverer the policy, the more traffic it funnels into the black hole. Health checking normally rescues this in about a second, so it is switched off here to show what the policy does unaided.

The policies

The statelessness tax

Horizontal scaling only works once state leaves the process. Three ways to keep a user's session across a fleet, each with a measured price rather than an opinion.

It gets worse as you grow

With sessions in process memory the wrong-instance rate is (n−1)/n. In-process state does not merely fail to scale — it punishes scaling.

Affinity is not balance

Stickiness fixes correctness and creates hot instances. No load-aware policy can help while the key must go where it must go.

Consistent hashing

Not better balance — far less disruption. Losing one instance of four moves about a quarter of your users instead of nearly all of them.

Health checks

Liveness asks whether the process is alive. Readiness asks whether it should get traffic. A deep check asks whether its dependencies work. Confusing the three is how a dependency blip becomes a total outage.

The cascade

Point readiness at the shared database, break the database, and watch a fleet in which nothing is wrong eject itself.

The faults, and what each one is for

Failure, as a user sees it

Constant arrival rate throughout, so this is what someone using the service would have experienced — not what a patient benchmark would have reported. An instance breaks after the first window and is revived after the third.

The error budget

Errors do not stop the moment an instance is ejected. The window between breaking and being removed is set by your detection parameters, not by the fault.

Recovery is the forgotten half

A revived instance comes back cold. Give it a full share immediately and it fails again — you have built an oscillator.

Drain beats kill

Stop receiving traffic before you stop accepting it. On Windows there is no SIGTERM contract, so the drain has to be asked for at the application layer.
