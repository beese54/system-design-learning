How a query actually runs

SQL says what you want, never how to get it. The planner decides how, by estimating the cost of each option from table statistics. EXPLAIN shows you the plan it chose and what it guessed; EXPLAIN ANALYZE runs the query and shows what really happened. The gap between planned and actual rows is where slow queries hide.

Writes are wrapped in a transaction and rolled back, so it is safe to plan an UPDATE.

Seq Scan

Read every row in the table. Correct at any size, and the right choice when you genuinely want most of the rows. A disaster when you wanted twelve.

Index Scan / Bitmap Heap Scan

Use an index to find candidate rows, then fetch them. Bitmap variants collect many matches first so the heap is read in page order.

Index Only Scan

The index held every column the query needed, so the table was never touched. The cheapest read there is — and it depends on VACUUM keeping the visibility map fresh.

Indexes, added and dropped against a live million-row table

An index is not free storage magic. It is a permanent tax on every write, paid so that some read gets cheaper. Nobody bills you for the tax explicitly, which is why databases accumulate indexes nobody uses. The loop here: probe the query, add the index, probe again, then measure what the write side lost.

Isolation levels, one step at a time

An isolation anomaly is a story about interleaving: A does this, B does that, then A does this and gets an answer no single statement could ever produce. You have to watch it in order. Below are two real Postgres backends with their own PIDs — nothing here is simulated. Run a scenario, then change the isolation level and run the identical script again. The script never changes; only the level does. That is what makes the comparison mean something.

      READ COMMITTED

      Postgres' default. Each statement sees a fresh snapshot. Cheap, and permits non-repeatable reads, phantoms, lost updates and write skew.

      REPEATABLE READ

      One snapshot for the whole transaction. In Postgres this also stops phantoms, which the SQL standard does not require. Still permits write skew.

      SERIALIZABLE

      Guarantees the result matches some serial order. The only level that catches write skew. Costs you 40001 errors, which your code must retry.

      40001 is not a failure

      A serialization error means the database refused to corrupt your data. The bug is not having a retry loop around the transaction.

      idle in transaction

      A session that ran BEGIN and then went to lunch. It holds every lock it has taken and blocks VACUUM from cleaning up. Set idle_in_transaction_session_timeout and stop guessing.

      Lock ordering

      Deadlocks are not caused by too many locks. They are caused by two code paths taking the same locks in different orders. Fix the order, not the timeout.

      Long transactions are the cost

      The damage a transaction does is measured by how long it holds locks, not by how much work it does. Never keep one open across a network call to something you do not control.

      The N+1, now with a database underneath it

      In the API Design course the naive REST bar was 4 HTTP round trips. That was half the bill. Each of those requests also ran queries — and this is where you see how many. Same artist page, three implementations, real query counts.

      Fewer queries is not automatically better

      The single-query version shapes JSON in SQL. It is the fastest and the hardest to maintain. That is a real trade, not a free win.

      N+1 hides behind good code

      Nothing looks wrong in a loop that fetches one album's tracks. The bug is only visible when you count statements, which is why counting them is a habit worth having.

      Connections are not free, and the pool has a floor

      Every Postgres connection is a forked backend process on the server — tens of milliseconds and a few megabytes to create. A pool amortises that away. But a pool also has a size, and asking for more concurrency than it has does not fail: it queues, silently, inside your application. That queue is latency your database metrics will never explain, because from Postgres' point of view nothing was slow.

      Sizing

      Start near cores × 2, then measure. A bigger pool is not a faster database — past a point you are just moving the queue from your app onto the server.

      Every app instance has its own pool

      Ten pods × a pool of 20 is 200 connections. Compare that with max_connections before you scale out, not after.

      Where the queue hides

      Slow endpoint, fast queries, idle CPU: look at pool wait time. It is one of the most commonly missed sources of production latency.
